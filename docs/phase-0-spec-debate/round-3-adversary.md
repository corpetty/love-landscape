# Round 3 — Adversary

1. **Milestone create is not idempotent even though the row is.** No conditional-on-insert rule, no unique constraint catching replays (`client_result_id` absent from milestones). Retries/queue flushes after in-session success → N create milestones per person; B counts the same person in multiple weeks; the velocity check fires on phantom bursts. One-sentence fix, absent.

2. **`occurred_at` = flush time corrupts the gate windows.** (a) Shakedown completions flushing after freeze leak into the gate window the PRD excludes; (b) B's trend is distorted rightward — outage/recovery manufactures an uptrend in the momentum diagnostic; (c) mass flush ≈ bot spike under the velocity check. Fix: client sends `completed_at`; gate SQL uses it bounded by receipt. Absent.

3. **Create-on-demand writes NULL status/variant and inflates H in the PASS direction.** `ll-results-v1` stores no status/variant, so feature-triggered creates carry none. Trace: single with failed eager write joins waitlist → on-demand create (status NULL) + waitlist_join → in H's numerator, absent from its denominator. Gate metric, 20% bar, biased upward in exactly the engaged-singles population — the one direction the spec promises never to bias. Same hole kills F0.7's variant attribution. Also unspecified: whether a loaded partner code can reach a feature that mints a create — if yes, metric A is mintable by people who never took the assessment.

4. **The claim checkboxes are a fiction at the milestone layer.** Milestones carry session-granular person_key and no result reference; excluding a partner's result still re-keys all of the session's milestones — including the partner's `status='single'` create — permanently and silently (the partner's later claim matches zero rows). The mitigation operates on `results`; the gate reads `milestones`. Plus the re-key UPDATE races a concurrent queue flush (one human → two persons, no repair).

5. **Metric E is structurally uncomputable for inline-OTP users.** The waitlist's inline OTP mints a verified user whose `signup` (user-keyed) never joins their `create` (session-keyed) unless the optional claim UI runs. E driven toward KILL regardless of true behavior. Either inline flows perform an implicit claim of the current result, or E's definition changes — the spec does neither and would evaluate the gate wrongly.

6. **sharedView's gating fixes the wrong axis — the pathname leaks.** CTA → assessment → owner results screen → URL-rewrite effect fires on `/r/slug` → `/r/slug?code=THEIRS`, which re-shared serves the original owner's OG/share and shadows the visitor's code (`__SHARE__` vs `?code=` precedence unspecified). Mid-assessment refresh reloads `/r/slug`, re-fires `share_page_view` without a symmetric `assessment_start` — puncturing D's "bias cancels" claim. Fix: CTA `replaceState` to `/` + one-shot `__SHARE__` consumption. (Asset paths/CSP fine — root-absolute, no CSP.)

7. **Schedule still hides ~15–25h and one landmine.** Unbudgeted: `gate_metrics()` + freeze artifact (the spec's own success condition — no line item); claim-UI "mini preview" (a thumbnail renderer); OTP-send abuse control; ~8–12 writing hours land pre-push on the same human (true weekly load ~17–20h vs. the 10–15 envelope). `code-reference-dist` is pre-conceded dead — then say the anomaly review is velocity+IP now, not at freeze. **Landmine:** WA MHMDA gets 3h to *review* with no decision rule if the answer is "applies" — for a product inferring relational-psychology parameters, a positive finding demands consent architecture that is weeks, not hours, and it sits one week before freeze.

8. **New v3 privacy/security gaps.** (a) The deletion "salted hash" is pseudonymization unless the salt is per-deletion-random-and-discarded — unstated, and the privacy page will assert "anonymous," a checkable claim under the regimes the spec name-drops. Both re-key operations also contradict the declared "never updated" invariant. (b) The retry queue persists code + relationship status in plaintext localStorage indefinitely (no TTL), readable on shared devices. (c) Account deletion doesn't invalidate the device queue — a zombie flush resurrects a row for a person who exercised erasure; no tombstone check. (d) No cap on OTP *sends*: an attacker can burn the Resend quota and torch the fresh domain's reputation in launch week — an H/E outage in disguise.

9. **Net gate verdict:** H inflatable past truth (PASS-direction — the worst kind), E deflatable toward KILL, B and the shakedown boundary corrupted by flush timestamps, A/status misattribution locked in by session-granular re-keying. All are the default behavior of the spec's own text on its most common failure path (a failed eager write on mobile). Each has a one-to-three-sentence fix; until they land, the "one committed SQL function over an append-only table" success condition is satisfied in form and violated in substance.
